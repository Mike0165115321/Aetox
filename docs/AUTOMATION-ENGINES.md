# เครื่องมืออัตโนมัติภายนอก — สิ่งที่ตรวจของจริงมาแล้ว

> เอกสารอ้างอิง ไม่ใช่ทิศทาง ทิศทางอยู่ที่ [COMPANY.md §7](../COMPANY.md) และ
> [DECISIONS.md §92.3](DECISIONS.md) — ที่นี่คือ *ข้อเท็จจริงของ API* ที่ค้นและ
> ตรวจสอบแบบไล่หักล้างมาแล้วเมื่อ 9 ส.ค. 2569 เขียนไว้เพราะเป็นของที่แพงที่สุด
> ในการทำสไลซ์นี้ และเป็นของที่จะถูกลืมเร็วที่สุด
>
> **ทุกข้อล่างนี้ผ่านการให้คนที่สองพยายามหักล้างแล้ว** ข้อที่หักล้างได้อยู่ท้ายไฟล์

## n8n — ทำแล้ว (`internal/automation/n8n`)

| | |
|:--|:--|
| ผู้ใช้กรอก | origin เช่น `http://localhost:5678` |
| API อยู่ที่ | `{base}/api/v1` |
| หัวข้อยืนยันตัวตน | `X-N8N-API-KEY: <คีย์ดิบ>` — **ไม่ใช่ Bearer** |
| ผู้ใช้สร้างคีย์ที่ | Settings → n8n API (คีย์ **มีวันหมดอายุ** ที่ตั้งตอนสร้าง) |
| เช็คว่าเชื่อมได้ | `GET /workflows?limit=1` |
| สร้าง | `POST /workflows` → **ตอบ 200 ไม่ใช่ 201** |
| แก้ | `PUT /workflows/{id}` — **แทนที่ทั้งตัว ไม่มี PATCH** |
| เปิด/ปิด | `POST /workflows/{id}/activate` · `/deactivate` |

**บอดี้ที่เล็กที่สุดที่สร้างได้:** `{"name":"...","nodes":[],"connections":{},"settings":{}}`
— `settings` **บังคับ** แม้ทุกคีย์ข้างในจะไม่บังคับ

### สามข้อที่ทำให้พังถ้าไม่รู้

1. **อ่านมาแล้วเขียนกลับตรง ๆ ไม่ได้** ฟิลด์อ่านอย่างเดียว (`id` `active` `createdAt`
   `updatedAt` `isArchived` `versionId` `triggerCount` `tags` `meta`) **ถูกปฏิเสธ ไม่ใช่ถูกเมิน**
   และ schema เป็น `additionalProperties: false` → ต้องประกอบบอดี้จาก **allowlist**
   ไม่ใช่ลบฟิลด์ออกจากผลลัพธ์ที่ GET มา (`writableFields` ใน `workflows.go`)
2. **สร้างให้ทำงานเลยไม่ได้** `active` อ่านอย่างเดียวตอนสร้าง → สร้างเสร็จต้องสั่ง activate แยก
3. **`connections` คีย์ด้วย *ชื่อ* โหนด และซ้อนสองชั้น**
   `{"A":{"main":[[{"node":"B","type":"main","index":0}]]}}` — ชั้นนอกคือพอร์ตขาออก
   ชั้นในคือรายการที่แตกไป ผิดตรงนี้ = workflow ผ่านการตรวจแต่โหนดไม่ต่อกัน

### ไม่มีทางถาม schema ของโหนด — ยืนยันแล้ว

ไล่ทุก path ใน `openapi.yml` แล้ว ไม่มี `/node-types` ไม่มีอะไรคืน `INodeTypeDescription`
`/api/v1/discover` ที่ชื่อชวนเข้าใจผิดคือ "ค้นหาความสามารถของ API" ไม่ใช่ของโหนด
คำอธิบายโหนดมีจริงแต่อยู่หลัง internal API ที่ยืนยันตัวตนด้วย cookie `n8n-auth` เท่านั้น
(ต้องมีอีเมล+รหัสผ่านของผู้ใช้) — **ไม่เดินทางนั้น**

`parameters` ของโหนดถูกตรวจแบบ `additionalProperties: true` แปลว่า **พารามิเตอร์มั่ว
หรือโหนดที่ไม่มีอยู่จริง จะถูกรับตอนเขียน และไปพังตอนรัน** นี่คือเหตุผลที่คำอธิบาย
เครื่องมือใน `internal/skill/n8n_tools.go` บอกโมเดลตรง ๆ ให้ไปอ่าน workflow ที่มีอยู่ก่อน

**ยังไม่มี:** ลูป สร้าง → ทดลองรัน → อ่าน error → ซ่อม
(`GET /executions?status=error&workflowId=` แล้ว `GET /executions/{id}?includeData=true`)
อันนี้คือสิ่งเดียวที่จะรู้ได้จริงว่า workflow ที่เอไอเขียนใช้ได้ไหม

## Windmill — ทำแล้ว (`internal/automation/windmill`) เข้าเป็น connection เหมือน n8n (§97.1)

> **ตัดสินแล้ว 10 ส.ค. 2569:** เขียนไคลเอนต์เอง ไม่ผ่าน MCP ของ Windmill
>
> ทางที่ไม่ได้เลือกและเหตุผล เก็บไว้เพราะมันคือ fallback ที่มีเหตุผลเขียนไว้แล้ว:
> Windmill มี MCP server อยู่ในตัวสินค้า ใช้ได้ถึง Community Edition มี
> `createFlow` / `updateFlow` ครบ คุยด้วย streamable HTTP + header ซึ่ง
> `internal/mcp/client.go` พูดได้อยู่แล้ว — ถูกกว่ามาก **แต่**มันทำให้สองเอนจินมาถึง
> คนละทาง: คนละกฎสิทธิ์ คนละรูปใน `tool_runs` คนละหน้าตั้งค่า และพรอมป์ต้องอธิบาย
> ว่าอันไหนเป็นอันไหน ผู้ใช้จะไม่ได้มี "เอนจินออโตเมชั่นที่เชื่อมแล้ว" แต่มีของสองชนิด
> ที่ทุกชั้นถัดไปต้องรู้จักแยก — ซึ่งคือรอยต่อที่ §92.3 เขียนไว้เพื่อไม่ให้เกิด
>
> URL ของ MCP (ถ้าวันหนึ่งต้องกลับไป): `<base>/api/mcp/w/<workspace-id>/mcp?token=<token>`

### สเปกที่ตรวจไว้ — ตอนนี้คือสิ่งที่ `internal/automation/windmill` ทำจริง

| | |
|:--|:--|
| ผู้ใช้กรอก | origin เท่านั้น ไม่มี path — `http://localhost:8000` |
| API อยู่ที่ | `{base}/api` |
| หัวข้อยืนยันตัวตน | `Authorization: Bearer <token>` |
| ผู้ใช้สร้าง token ที่ | `{base}/#user-settings` — **บอกให้เว้น scope ว่าง และอย่าติ๊ก read_only** |
| เช็คว่าเชื่อมได้ | `GET /api/users/whoami` → **`email` คือตัวระบุบัญชี** (`username` ไม่บังคับ) |
| workspace | `GET /api/workspaces/list` → ใช้ฟิลด์ **`id` ไม่ใช่ `name`** (ใช้ name จะได้ 404 ที่อ่านเหมือนปัญหาสิทธิ์) |
| list flow | `GET /api/w/{ws}/flows/list` |
| อ่าน | `GET /api/w/{ws}/flows/get/{path}` |
| สร้าง | `POST /api/w/{ws}/flows/create` → **201 บอดี้เป็น text/plain** |
| แก้ | `POST /api/w/{ws}/flows/update/{path}` → **POST ไม่ใช่ PUT** บอดี้ text/plain |

**บอดี้ที่เล็กที่สุด:** `{"path":"u/<username>/ชื่อ","summary":"","value":{"modules":[]}}`
path ถูกบังคับรูปแบบฝั่งเซิร์ฟเวอร์: `^[ufg](/[\p{Alphabetic}\p{Nd}_-]+){2,}$` ยาวไม่เกิน 255
ไม่มีจุด ไม่มีเว้นวรรค — **ควรตรวจฝั่งเราก่อน** เพราะ 400 จากเซิร์ฟเวอร์อ่านไม่รู้เรื่อง

### สี่ข้อที่ต้องระวังตอนเขียน

1. **path ของ flow ใส่ลง URL แบบดิบ** route เป็น wildcard — **ห้าม percent-encode
   เครื่องหมาย `/`** ต่อ URL เป็นสตริงตรง ๆ อย่าให้ `url.URL` มาจัดการ path ให้
2. **ตอน update ต้องส่ง `path` `summary` `value` ครบเสมอ** — เวอร์ชันเก่ารับ
   `OpenFlowWPath` ที่ `path` บังคับ ส่งครบแล้วใช้ได้ทั้งเก่าและใหม่
3. **create/update ตอบเป็น text/plain** อย่าเอาไป JSON-decode
4. **script คนละเรื่องกับ flow** — สร้างและแก้ใช้ `POST .../scripts/create` เหมือนกัน
   (ไม่มี endpoint update) ลบใช้ POST ส่วน flow ลบใช้ DELETE · **อย่าลบแล้วสร้างใหม่**
   มันทำลายประวัติและ schedule ที่ชี้อยู่

### เรื่อง schema: อย่าเอา openapi.json มาใช้ตรวจ input

`GET /api/openapi.json` เรียกได้จริงและบอก taxonomy ของ step ได้
(`rawscript` `script` `flow` `forloopflow` `whileloopflow` `branchone` `branchall`
`identity` `aiagent`) — **แต่ห้ามเอาไปใช้เป็นตัว validate**

เหตุผล: spec ที่เซิร์ฟเวอร์เสิร์ฟออกมา **ไม่ตรงกับ binary ที่กำลังเสิร์ฟมันอยู่**
เครื่องหนึ่งรายงาน `/api/version` = `v1.782.0` แต่ `openapi.json` จากเครื่องเดียวกัน
ประกาศ `info.version` = `1.740.0` — ห่างกันราว 43 รุ่น เพราะมันเป็นไฟล์ที่ commit ไว้
แล้วสร้างใหม่เป็นรอบ ๆ ไม่ได้เกิดจาก build **ถ้าเอาไป validate จะปฏิเสธของที่ถูกต้อง**
(ตัวอย่างจริง: `RawScript.language` เครื่องหนึ่งเสิร์ฟ 23 ค่า ขาด `bunnative` ที่มีจริง)

**ไม่มีทะเบียนชนิดโหนดเหมือน n8n** — step คือโค้ดหรือการอ้างถึงของที่รันได้
จะรู้ arg ของเป้าหมายต้องถามทีละอัน (`scripts/get/p/{path}` → `schema`)

**สิ่งที่ยังไม่ได้ทำสำหรับ Windmill:** script (คนละทรัพยากรกับ flow) · archive/delete ·
ประวัติเวอร์ชัน (`flows/history/p/{path}` — ซึ่งคือทางย้อนกลับที่ควรมี) · และลูป
สร้าง → ทดลองรัน → อ่าน error → ซ่อม เหมือนที่ n8n ก็ยังขาด

## หนี้ที่ปิดแล้ว: `needs:` รองรับ "อย่างน้อยหนึ่งใน" — 10 ส.ค. 2569

เอเจน `automation` ประกาศ `needs: connection:n8n | connection:windmill` แล้ว — `|` แปลว่า
**มีอันใดอันหนึ่งก็พอ** (§97.2) คนที่รัน Windmill อย่างเดียวไม่โดนเตือนว่าขาด n8n
อีกต่อไป

ทางที่เลือกคือทางแรกในสองทางที่บันทึกไว้เดิม (แก้ `internal/subagent/needs.go`)
ไม่ใช่ `connection-kind:` เพราะการแยกเป็น "ชนิด" ต้องมีทะเบียนที่สองมาบอกว่าเจ้าไหน
นับเป็นชนิดไหน — ส่วน `|` อยู่ในบรรทัดที่มันพูดถึง อ่านแล้วรู้เลย

**ตอนไม่มีสักเจ้า รายงานอันเดียว ไม่ใช่ลิสต์** และอันที่รายงานคืออันที่**ใกล้ใช้ได้ที่สุด**
(`closeness`) — บัญชีที่เชื่อมแล้วเหลือกดปุ่มเดียว ชนะของที่ยังไม่ได้ติดตั้ง
ถ้ารายงานตามลำดับที่เขียน ผู้ใช้จะถูกส่งไปทำของแพงทั้งที่ของถูกอยู่ตรงหน้า

อย่าเผลอแก้ด้วยการ**ลบ** `needs` ทิ้ง — จะได้เอเจนที่ไม่มีเครื่องมือแล้วเงียบ
ซึ่งคือสิ่งที่กลไก `needs` ถูกสร้างมาเพื่อไม่ให้เกิด

## ที่หักล้างได้ระหว่างตรวจ — อย่าเชื่อของเดิม

- **scope ของ n8n เป็นของ Enterprise** คีย์บน Community มีสิทธิ์เต็มทุกอย่างเสมอ
  อย่าเขียน logic ตัดสินสิทธิ์จากมัน
- **`projectId` / `parentFolderId` ของ n8n เป็นของเสียเงิน** ใช้ไม่ได้บน CE เปล่า ๆ
- **`/activate` ถูกมาร์ค deprecated แล้วใน master** (ให้ใช้ `/publish` แทน) แต่ยังเป็น
  ตัวเลือกที่ถูกสำหรับความเข้ากันได้ — ตรวจความสามารถจาก `openapi.yml` ของเครื่องนั้น
- **409 มีเอกสารบน `/activate` ด้วย** ไม่ใช่แค่ `/publish`
- **URL เอกสาร `docs.n8n.io/api/*` ตายหมดแล้ว** ของจริงคือ `docs.n8n.io/connect/n8n-api/...`
  — **ห้ามเอา URL เก่าไปใส่ใน UI**
- **n8n เป็น fair-code (Sustainable Use License) ไม่ใช่ open source** มีผลกับการทำ
  ผลิตภัณฑ์ขายรอบมัน — เรื่องกฎหมาย ไม่ใช่เรื่องเทคนิค แต่ควรอ่านก่อนขาย
- **`u/<username>/...` ของ Windmill คือพื้นที่ส่วนตัวของคนนั้น** ไม่ใช่ที่ทำงานร่วม
  ถ้าจะเขียนลง `f/<folder>/` โฟลเดอร์ต้องมีอยู่จริงและผู้ใช้ต้องมีสิทธิ์เขียน
  ไม่งั้นจะเด้งออกมาเป็น permission error ผ่าน Postgres RLS ไม่ใช่ 404 สวย ๆ
