# 🚀 Aetox v0.9.3

v0.9.2 ตอบว่า *บทสนทนาอยู่ที่ไหน* และ *คำตอบเป็นอะไรได้บ้าง* รุ่นนี้ตอบคำถามที่ตามมาทันที คือ
**เอเจนตัวหนึ่งต้องมีอะไรถึงจะทำงานได้จริง** และ **ทำไมเอเจนตัวเดียวกันถึงตอบไม่เหมือนกันเมื่อ
เข้ามาคนละทาง**

คำตอบของข้อสองน่าอายที่สุดในรุ่นนี้ และเจอด้วยการวัด: เอเจนที่ผู้ใช้เปิดคุยเองได้คำสั่งตั้งต้นยาว
15,106 ตัวอักษร ส่วนเอเจนตัวเดียวกันที่ผู้ช่วยหลักสั่งงานได้ 4,429 ตัวอักษร คือไม่รู้ว่าไฟล์ที่ไม่ระบุ
ที่อยู่จะไปโผล่ตรงไหน ไม่รู้กฎของเครื่อง ไม่รู้กฎของโปรเจกต์ **และไม่มีใครเคยตัดสินใจให้เป็นแบบนั้น**
ทางที่สองแค่ไม่เคยถูกต่อเข้ากับตัวประกอบคำสั่งตั้งต้น

## 1. หน้าการเชื่อมต่อ: บัญชีที่เอเจนทำงานแทนคุณได้

หน้าใหม่ใน **ตั้งค่า → การเชื่อมต่อ** เริ่มที่ GitHub

พอเชื่อมบัญชีแล้ว โทเคนจะถูกเก็บใน **คลังเดียวกับการล็อกอินโมเดล** เข้ารหัสด้วย DPAPI ไม่ใช่
ไฟล์ตั้งค่าธรรมดา เหตุผลเขียนไว้ในโค้ดตั้งแต่ก่อนหน้านี้แล้ว คือไฟล์ตั้งค่ามักถูกคัดลอกไปแปะใน
รายงานบั๊กและถูกซิงก์ข้ามเครื่อง ความลับจึงห้ามอยู่ในนั้น

สิ่งที่ได้ทันทีโดยไม่ต้องมีเครื่องมือใหม่สักตัว:

| | ก่อน | หลัง |
|---|---|---|
| repository ส่วนตัว | ❌ | ✅ |
| โควตา | 60 ครั้ง/ชม. | **5,000 ครั้ง/ชม.** |

**Aetox ตรวจโทเคนกับ GitHub ก่อนบันทึกเสมอ** โทเคนที่ผิดจะไม่ถูกเก็บ ไม่งั้นมันจะไปโผล่เป็น
ข้อความ "หา repo ไม่เจอ" กลางงานในอีกสามวัน

**แถว "ใครได้ใช้"** ทุกบัญชีมีแถวเลือกว่าโต๊ะไหนและเอเจนตัวไหนได้ใช้ ใช้รูปแบบเดียวกับเซิร์ฟเวอร์
MCP เป๊ะ เพราะเป็นคำถามเดียวกัน คือของที่ต่อมาจากข้างนอก ใครได้ใช้

- **ปิด = เครื่องมือหายจากรายการของโต๊ะนั้นไปเลย** ไม่ใช่ "ถามก่อน" เพราะประตูที่เปิดไม่ได้ไม่ควร
  ให้โมเดลเห็น
- **ยังไม่เคยตั้ง = ทุกโต๊ะได้ใช้** การอัปเกรดต้องไม่แย่งของที่ใครเคยมีไป
- **เอเจนไม่ได้อัตโนมัติ** เอเจนได้ของเพราะมีคนยื่นให้ ความเงียบไม่ใช่การอนุญาต

## 2. เอเจน `github` และมาตรฐานที่มันเป็นตัวแรก

เอเจนตัวใหม่ที่ดูแลงานฝั่ง GitHub ทั้งหมด ทั้งเปิดและรีวิว PR ไล่หาสาเหตุที่ CI แดง จัดการ issue
และตั้งค่า repo ให้ได้มาตรฐาน

ความรู้ของมันอยู่ใน **โฟลเดอร์ของตัวเอง** ไม่ใช่ในคำสั่งตั้งต้น เป็นสกิลสี่ใบที่เอเจนตัวอื่นมองไม่เห็น:

| สกิล | มีอะไร |
|---|---|
| `repo-standards` | ไม่มี LICENSE = ไม่มีใครใช้ได้ตามกฎหมาย · README · CODEOWNERS · SECURITY.md · การป้องกันแบรนช์ · Dependabot โดย **เรียงตามว่าอะไรพังก่อนถ้าไม่มี** ไม่ใช่ตามที่คนพูดถึงบ่อย |
| `pr-workflow` | เขียนคำอธิบาย PR ตามลำดับคำถามที่คนรีวิวถามจริง และการ merge เป็นการตัดสินใจของคนอื่น |
| `ci-triage` | อ่านบันทึกจากล่างขึ้นบน · แยกสี่แบบคือพังจริง / บังเอิญ / เครื่องมีปัญหา / ตั้งค่าผิด · **รันซ้ำสองครั้งคือเพดาน ครั้งที่สามคือความหวัง** |
| `issue-hygiene` | ตั้งชื่อเรื่องให้ค้นเจอ · คัดกรองด้วยสามคำถาม · ป้ายสองแกนก็พอ |

**`needs:` เป็นการประกาศ ไม่ใช่การให้สิทธิ์** เอเจนบอกได้แล้วว่าตัวเองขาดอะไร และเส้นที่ห้ามข้าม
คือการประกาศไม่เคยให้สิทธิ์อะไรเลย สิทธิ์ยังมาจากที่เดียวเหมือนเดิม เหตุผลคือบทเรียนที่เขียนไว้
ก่อนแล้ว: ไฟล์ที่คอมไพล์มาก่อนที่ของผู้ใช้จะมีอยู่ อาจอ้างถึงของที่ไม่มีสักตัว แล้วกรองทุกอย่างทิ้ง
เงียบ ๆ การประกาศที่ชี้ไปหาของที่ไม่มีจึงได้แค่ *ประโยคบนจอ* ไม่มีทางทำให้รายการเครื่องมือว่าง
โดยไม่มีใครรู้

**ขาดของแล้วให้ ขอ แล้วทำส่วนที่เหลือ** ข้อความรุ่นแรกเขียนว่า *"บอกว่าขาดอะไรแล้วหยุด"* ซึ่งผิด
และผิดในแบบที่ควรจดไว้ เพราะมันเปลี่ยนผู้เชี่ยวชาญให้กลายเป็นยามเฝ้าประตู เอเจน GitHub ที่ไม่มี
โทเคนยังมีเครื่องมือไฟล์ของตัวเอง มีสกิลสี่ใบ และ **คำถามส่วนใหญ่เรื่อง repo ไม่ต้องใช้บัญชีเลย**

รูปที่ถูกคือสามข้อเรียงกัน: **ขอ → ทำส่วนที่ไม่ต้องใช้มัน → ห้ามส่งผลลัพธ์ราวกับว่ามีของชิ้นนั้น**
มีเส้นตายเส้นเดียวคือข้อสาม เพราะเป็นความพังที่ปลายทางจับไม่ได้ และรูปทั่วไปของกฎนี้อยู่ใน
คำสั่งตั้งต้นของทั้งผู้ช่วยหลักและทุกเอเจนแล้ว ไม่ใช่แค่ของเอเจน `github`

> ปฏิเสธทั้งงานเพราะขาดชิ้นเดียว กับทำงานจนจบทั้งที่แอบขาดชิ้นหนึ่ง **คือความผิดเดียวกัน
> เล่าคนละแบบ**

## 3. ทางเดียว: เอเจนตัวเดียวกัน คำสั่งตั้งต้นก้อนเดียวกัน

วัดก่อนแก้:

| | ก่อน | หลัง |
|---|---|---|
| ผู้ใช้เปิดคุยตรง | 15,106 | 15,106 |
| ผู้ช่วยหลักสั่งงาน | **4,429** | **15,106** |

ตอนนี้การมอบงานประกอบคำสั่งตั้งต้นของลูก **ด้วยตัวประกอบตัวเดียวกับที่เซสชันใช้ประกอบของ
ตัวเอง** โดยเอาคำอธิบายงานของเอเจนไปนั่งช่องเดียวกับที่ทิศทางของโต๊ะนั่ง ไม่ได้คัดลอกโค้ดไปไว้
อีกที่ แต่ยืมตัวประกอบไปใช้ ที่ประกอบมีที่เดียวในระบบ และมีคนเรียกคนเดียว

**ตำแหน่งก็สำคัญไม่แพ้กัน** คำอธิบายงานย้ายจากลำดับที่ 13 มาอยู่ที่สอง ต่อจากตัวตนเสมอ เดิมมัน
ไปนั่งอยู่ที่ 68% ของคำสั่งตั้งต้น แล้วโมเดลก็ตอบจากบรรทัดแรกที่มันอ่านเจอ ซึ่งเป็นบรรทัดของ
ผู้ช่วยหลัก **เอเจนคือ Aetox ที่เชี่ยวชาญเฉพาะทาง ไม่ใช่คนอื่น** สิ่งที่คำอธิบายงานต้องการคือถูก
*อ่าน* ไม่ใช่ไปแทนที่ตัวตนข้างบน

ของแถม: เพดานความยาวของคำอธิบายงานเคยวัดกับตัวเปล่า ซึ่งเป็นตัวเลขที่ผิดมาตลอด ตอนนี้วัดกับ
คำสั่งตั้งต้นที่ประกอบเสร็จแล้ว

## 4. MCP ต่อตอนใช้ ไม่ใช่ตอนเปิดแอป

การตั้งว่าใครได้ใช้ เคยตัดสินแค่ว่า **ใครเห็น** เครื่องมือ ไม่เคยตัดสินว่าจะต่อหรือไม่ต่อ เซิร์ฟเวอร์ที่
วางไว้ให้เอเจนตัวเดียวจึงถูกเปิดทุกครั้งที่เปิดแอป ของทุกคนที่ตั้งค่าไว้ ทั้งที่ทั้งวันไม่มีใครแตะเอเจน
ตัวนั้นเลย สำหรับเซิร์ฟเวอร์ที่มี 90 เครื่องมือ นั่นคือการจับมือและดึงรายการทั้งชุดมาเผื่อไว้เฉย ๆ

ตอนนี้เซิร์ฟเวอร์ที่วางไว้ให้เอเจนอย่างเดียวจะ **ขึ้นตอนมีคนเรียกเอเจนตัวนั้นจริง** เรียกจากทางไหน
ก็เรียกที่เดียวกัน

**ด่านขออนุญาตไม่ต้องรอ** เพราะกฎถูกสร้างจากชื่อเซิร์ฟเวอร์ล้วนโดยไม่ต้องต่อ เซิร์ฟเวอร์ที่ยังหลับ
อยู่จึงถูกกั้นไว้ก่อนตื่น ไม่มีช่องที่เครื่องมือโผล่มาก่อนกฎ

ผลพลอยได้ที่สำคัญกว่าที่คิดคือ **การขออนุญาตจะเกิดตอนใช้จริงครั้งแรก ไม่ใช่ตอนเปิดแอป** ซึ่งเป็น
จังหวะเดียวที่คำถาม "จะให้สิทธิ์ไหม" มีบริบทให้ตอบ

## 5. คำศัพท์: เอเจน กับ ซับเอเจน

หน้าจอเดียวเคยมีสามคำปนกัน รุ่นนี้เหลือสองคำสำหรับสองชนิด ทั้งในหน้าจอ เอกสาร และคำสั่งที่ส่ง
ให้โมเดล สิ่งที่เจ้าของเคาะไว้ตั้งแต่ 6 ส.ค. คือ *สองชนิด* ไม่ใช่ตัวสะกด การเปลี่ยนคำจึงไม่ได้ล้ม
การตัดสินใจเดิม

และไฟล์เอเจนเหลือแค่ **ตัวตน + เครื่องมือ + สกิล**:

- หัวข้อที่สอนเอเจนให้ทนกับข้อจำกัดของช่องทางที่ถูกเรียก ถูกลบออกทั้งสี่ไฟล์ เพราะมันแก้ผิดชั้น
  ช่องทางที่ต่างกันไม่ควรกลายเป็นสองบุคลิกในคำสั่งตั้งต้น
- **ฟิลด์ระบุโต๊ะหายไปจากทุกไฟล์** เพราะที่อยู่ของไฟล์บอกชนิดอยู่แล้ว การเขียนฟิลด์นี้ทำได้อย่าง
  เดียวคือทำให้ผิด และผิดแบบเงียบ คือไฟล์ยังอ่านผ่าน ยังอยู่ในรายการ แต่หายไปจากหน้าทีม จาก
  ช่องเลือกในหน้าแชท และจากทุกทางที่ผู้ใช้เดินเข้าได้ ตอนนี้มีเทสต์กันความพังแบบนี้ไว้แล้ว
