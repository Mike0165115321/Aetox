# 🚀 Aetox v0.8.7 Release Notes — ซ่อมของที่ v0.8.6 ทำพัง และซ่อมหน้าปัดที่พังมา 6 วัน

รุ่นแก้บั๊กล้วน ไม่มีฟีเจอร์ใหม่ · **ถ้าคุณกดปุ่ม "ตอบใหม่" บน v0.8.6 ไปแล้ว รุ่นนี้ซ่อมฐานข้อมูลให้อัตโนมัติตอนอัปเกรด**

### 1. 🔴 กด "ตอบใหม่" ครั้งเดียวทำฐานข้อมูลเสียหาย (ของใหม่ใน v0.8.6)

* v0.8.6 คือรุ่นแรกที่ `UPDATE messages.text` — ตอนผู้ใช้ขอคำตอบใหม่ · แต่ `messages_fts` เป็น **external-content FTS5** ซึ่ง**ไม่ใช่ view**: ไม่มีอะไรอัปเดตมันนอกจาก trigger และมีแค่ AFTER INSERT กับ AFTER DELETE
* ผลไม่ใช่แค่ค้นหาเจอผลเก่า — **การลบที่พยายามปรับให้ตรงกันทีหลังทำให้ SQLite รายงานทั้งไฟล์ว่า `database disk image is malformed`** transaction ย้อนกลับ เซสชันนั้นลบไม่ได้ถาวร พร้อม `tool_runs` ที่มีเนื้อไฟล์และข้อความหน้าเว็บที่ดึงมาค้างอยู่ ตรงจุดที่ `sessions.go` สัญญาว่าจะลบพอดี
* **schema 5** เพิ่ม trigger AFTER UPDATE และใส่ให้ `tool_runs_fts` ไปด้วยแบบดักไว้ก่อน — ยังไม่มีใคร UPDATE `tool_runs` วันนี้ และต้นทุนของ trigger ที่ไม่เคยยิงเท่ากับศูนย์ เทียบกับการเจอเรื่องเดียวกันอีกรอบวันที่มีคนเพิ่ม
* migration เดียวกัน **rebuild ทั้งสอง index** เพราะคนที่กดปุ่มไปแล้วมี index เสียซึ่งไม่หายเอง
* ครึ่งหลังของความผิดพลาดเดียวกัน: `SwitchVariant` ย้ายข้อความแต่ทิ้งลำดับงานไว้ → สลับคำตอบแล้วเห็นคำตอบหนึ่งอยู่เหนือ tool call ของอีกคำตอบ · `SessionVariant` มี `Parts` ของตัวเองแล้ว — แต่ละครั้งที่ตอบมันทำงานของมันเอง และครั้งที่สองอาจอ่านคนละไฟล์
* เทสเดิมตรวจ `messages.text` กับ `messages.variants` และไม่เคยแตะ `messages_fts` เลย — นั่นคือเหตุผลที่มันหลุดออกไป เทสใหม่ล้มพร้อมข้อความจริง `database disk image is malformed (267)` ถ้าไม่มีตัวแก้

### 2. 🔍 CI ที่แดงมา 21 รอบ ไม่เคยเป็น data race เลย

* ทุกคนอ่านมันเป็น race รวมถึง ARCHITECTURE.md · **ไม่ใช่** — `desktop/mcp_test.go` สร้าง fixture ด้วย `go build` **หลังจาก** `isolateUserDirs` ชี้ `HOME` ไปที่ `t.TempDir()` ของเทสนั้นแล้ว ลูก `go` จึงคำนวณ `GOPATH=$HOME/go` และเขียน module cache ลงในนั้น ด้วยสิทธิ์ไดเรกทอรี 0555 ซึ่งเป็นสิ่งที่ Go ตั้งใจ และเป็นสิ่งที่ `t.TempDir` ลบไม่ได้: `unlinkat …/go/pkg/mod/…: permission denied`
* Windows ไม่เคยเห็น เพราะมันลบไดเรกทอรี read-only ได้สบาย
* **สามอย่างตามมาจากการที่มันไม่ใช่ race:** detector รันสะอาดกับ engine นี้มา 21 รอบและไม่มีใครมองเห็น · ubuntu เป็น job เดียวที่รันมัน ดังนั้น race จริงที่ลงพรุ่งนี้จะแยกไม่ออกจากอันนี้ · และ `verify.sh` **ข้าม** stage race บนเครื่องเจ้าของทั้งหมด (`go env CC` บอก gcc, `command -v gcc` ไม่เจอ) ขณะที่ ARCHITECTURE.md ยืนยันว่าช่องว่างนั้นปิดไปแล้วตั้งแต่ 2026-07-27
* ตอนนี้ fixture ระบุ `GOPATH/GOMODCACHE/GOCACHE` จริง จับไว้ตอน package init ก่อนที่ `t.Setenv` จะโกหกได้ · เร็วขึ้นด้วย: **14.0 วิ → 2.1 วิ** เพราะไม่ต้องโหลด dependency graph ใหม่ทุกรอบ
* skip ใน `verify.sh` **ส่งเสียงแล้ว** และเอกสารพูดสิ่งที่เป็นจริง
* macOS พังด้วยเหตุผลของตัวเองคนละเรื่อง — `npm run build` ตายด้วย Abort trap: 6 (heap ปริยายของ node ปะทะ `ts.worker` 7MB ของ monaco) · unix job ไม่เคยต้องการ bundle จริง มันไม่ได้รันเทส frontend และ `go:embed` ต้องการแค่ให้โฟลเดอร์มีอยู่ → เขียน stub แทน ตัด build ซ้ำซ้อนของ bundle ที่ไม่ขึ้นกับแพลตฟอร์มออกไป 2 ครั้งต่อ push

### 3. 🚦 ให้ pipeline ล้มได้จริง

* **`release.yml` เคยรันเทสแค่แพ็กเกจเดียว** (`internal/version`) และไม่ผูกกับ `ci` เลย — นั่นคือเหตุผลที่ v0.8.6 ถูกปล่อยจาก commit ที่ CI แดง · ตอนนี้รัน `go vet ./...` และ `go test ./...` ก่อนแพ็ก โดยวางไว้**หลัง** wails build เพราะนั่นคือสิ่งที่สร้าง `frontend/dist` ที่ `go:embed` ต้องการ
* ทุก action เล็งไปที่ Node 20 ที่ deprecated แล้ว รวมถึง `release.yml` ที่เป็นตัวปล่อยของ → `checkout@v5` `setup-go@v6` `setup-node@v5`
* `ci.yml` ได้ concurrency group และ `timeout-minutes` · **จงใจไม่ใส่ `release.yml`** เพราะยกเลิกการปล่อยของกลางคันแย่กว่าจ่ายค่า run ที่ถูกแทนที่

### 4. 📎 PDF ที่แนบไปไม่เคยถึงโมเดล

* `memory.Context.AddMessage` สร้าง message ใหม่ทีละฟิลด์ และคอมเมนต์ของมันเองเขียนไว้ว่านั่นแลกกับอะไร: *"this rebuild drops any field it does not name, and an attached image silently vanishing between the composer and the provider is a bug with no visible symptom"*
* `Documents` ถูกเพิ่มหลังคอมเมนต์นั้น **และตกลงไปในกับดักที่คอมเมนต์บรรยายไว้พอดี** — `cognitive.addUserTurn` วางเอกสารไว้บน message แล้วฟังก์ชันนี้โยนทิ้งหนึ่งการเรียกถัดมา ไม่มี provider ไหนได้รับเลยสักราย บนทุก wire format · โมเดลตอบจากชื่อไฟล์กับบริบทรอบข้าง ซึ่งเนียนพอที่จะไม่มีใครรายงาน
* แก้ด้วยการ **assign struct แล้วค่อย normalise** สามฟิลด์ที่เป็น string · เทสสองตัว: ตัวหนึ่งสำหรับไฟล์แนบเอง อีกตัวเดินทุกฟิลด์ของ `model.Message` ด้วย reflection และจะล้มในวันที่มีฟิลด์ใหม่ถูกดรอป — เทสแบบระบุฟิลด์ผ่านในวันที่เขียนแล้วเงียบตลอดกาล ซึ่งคือวิธีที่บั๊กนี้หลุด

### 5. ⚡ resolve path ในแซนด์บ็อกซ์เร็วขึ้น

* `resolveSandboxPath` เดิน `EvalSymlinks` สองรอบต่อการเรียก และโน้ตเหนือมันเขียนไว้ตั้งแต่ตอนแก้เรื่อง symlink containment ว่าให้ cache ฝั่งรากได้ *"if that stops being true"* — วัดจริงแล้วทั้งสองฝั่งจ่ายเต็มราคาทุกครั้ง
* ราก cache ได้เพราะ**ค่าเก่าทำให้ fail closed**: ถ้า component ของรากถูกเปลี่ยนหลัง cache อุ่นแล้ว เป้าหมายใต้ที่อยู่ใหม่จะ resolve ไปที่ที่รากใน cache ไม่ใช่ prefix อีกต่อไป และถูกปฏิเสธ · ฝั่งเป้าหมายยัง resolve สดทุกครั้ง
* ที่ได้มากกว่าคือ tautology: **8 จุดเรียกส่ง `.`** — working directory ของ shell, ฐานเดินของ grep และ glob, ตัวกันลบรากของ delete — และจ่าย symlink walk สองรอบเพื่อให้ตอบว่ารากอยู่ในราก มันเป็น string เดียวกัน ไม่มีคำถามกับ filesystem ให้ถาม

```
resolveSandboxPath(root, "a/b/c/file.txt")   2.51ms → 1.32ms
resolveSandboxPath(root, ".")                2.51ms → 1.6µs
```

* ตัวเลข Windows ที่ Defender สแกนทุก component ที่เปิด ซึ่งเป็นเหตุผลที่มันคุ้มค่าวัดตั้งแต่แรก · เทส containment ผ่านครบ
