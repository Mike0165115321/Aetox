# เด็คเป็น HTML — สัญญาของโครง

**สถานะ:** ตกลงแล้ว 2026-08-19 กำลังสร้าง ข้อ 1 ของลำดับสี่ข้อ

## ทำไมถึงย้าย

`slides_write` เขียน `.pptx` ได้สี่อย่าง — หัวเรื่อง บุลเล็ต รูปหนึ่งรูป โน้ต — และไม่มีสีบนสไลด์เลยแม้แต่จุดเดียว ทั้งที่ `themeXML` ประกาศ accent ไว้หกสี เจ้าของเปิดเด็คที่ได้แล้วสรุปสั้น ๆ ว่า "ตอนนี้มีแค่ตัวหนังสือ"

ทางที่ไม่เลือก คือขยาย `internal/ooxml/pptx.go` ให้รู้จักตาราง สี บุลเล็ตหลายชั้น เลย์เอาต์ นั่นคือการเขียน PowerPoint ขึ้นมาเอง ซึ่ง OFFICE-EXPORT-PLAN §8 ตัดออกตั้งแต่ต้น และเจ้าของยืนยันอีกครั้ง: *"ไม่ต้องเองสร้างพาเวอร์พอยต์"*

ทางที่เลือก คือแยกการเขียนออกจากการส่งออก โมเดลเขียน HTML ซึ่งเป็นภาษาที่มันคล่องที่สุด แล้วการส่งออกเป็นขั้นตอนต่างหากที่เล็งได้หลายฟอร์แมต แนวคิดเดียวกับ HyperFrames ที่ให้เอเจนต์เขียน HTML แล้วเรนเดอร์เป็นวิดีโอ ต่างกันตรงที่ของเราไม่มีแกนเวลา จึงถ่ายหนึ่งครั้งต่อสไลด์แทนสามสิบครั้งต่อวินาที และ HyperFrames ต้องลาก Puppeteer มาทั้งชุดเพื่อให้มีเบราว์เซอร์ ส่วนเรามี Chromium อยู่ในไบนารีแล้วจากงานคนละเรื่อง (WebView2 + แพตช์ `CapturePreview` ใน third_party/go-webview2)

## เครื่องหมายเดียวที่รับน้ำหนัก

**เอกสารที่มี `<section class="slide">` อย่างน้อยหนึ่งอัน คือเด็ค** ไม่มีอย่างอื่น

เคยคิดจะใส่ `<meta name="aetox-deck">` กำกับเพิ่ม แล้วตัดทิ้ง เพราะมันคือที่ที่สองที่ตอบคำถามเดียวกัน และวันที่สองที่ไม่ตรงกันคือวันที่ไม่มีใครรู้ว่าอันไหนถูก `section.slide` ต้องมีอยู่แล้วเพราะแพเนลกับตัวส่งออกต้องหาเส้นแบ่งสไลด์ จึงให้มันทำสองหน้าที่ไปเลย

ผลข้างเคียงที่ตั้งใจ: ไฟล์ `.html` ที่ไม่มีเครื่องหมายนี้ยังเปิดเป็นซอร์สในเอดิเตอร์เหมือนเดิม ไม่มีอะไรเปลี่ยนสำหรับหน้าเว็บธรรมดา

## กายวิภาคของสไลด์

ทุกอย่างในนี้เป็น HTML ปกติ ไม่ใช่ DSL ที่เราประดิษฐ์ โมเดลเขียนได้โดยไม่ต้องเรียน และคนแก้ด้วยมือได้

| ในไฟล์ | คืออะไร | ตัวลดทอนอ่านไปเป็น |
|---|---|---|
| `<section class="slide">` | หนึ่งสไลด์ | หนึ่ง `ooxml.Slide` |
| หัวเรื่องตัวแรกใน section | ชื่อสไลด์ | `Slide.Title` |
| `<li>` ใน section | บุลเล็ต | `Slide.Bullets` |
| `<img src="data:...">` | รูปบนสไลด์ | `Slide.Image` |
| `<aside class="notes">` | โน้ตผู้บรรยาย ไม่แสดงบนจอ | `Slide.Notes` |

ตารางนี้ตรงกับ `ooxml.Slide` หนึ่งต่อหนึ่งโดยตั้งใจ ตัวส่งออกเป็น `.pptx` จึงไม่ต้องเขียน OOXML ใหม่สักบรรทัด — `BuildPPTX` ตัวเดิมรับได้เลย และมันจะไม่โตอีกต่อไป

## ขนาด

สไลด์คือกล่อง **1280 × 720** ตายตัว อัตราส่วน 16:9

ตัวเลขถูกตรึงไว้ตรงนี้เพราะตัวส่งออกต้องรู้ค่าเดียวกันหมด: PDF ตั้งขนาดหน้าจากมัน (13.333 × 7.5 นิ้ว = 1280 × 720 ที่ 96dpi) และแพเนลย่อให้พอดีจอจากมัน ส่วน PNG/JPG **ไม่ได้ใช้ตัวเลขนี้** — มันวัดจาก `getBoundingClientRect()` ของสไลด์จริง เพราะสัญญาบอกว่าสไลด์ใหญ่แค่ไหน ไม่ได้บอกว่า CSS เรียงมันยังไง เด็คที่มีระยะห่างระหว่างสไลด์จะเพี้ยนสะสมทีละสไลด์ถ้าคำนวณเอา

## รูปต้องฝังมาในไฟล์

`<img>` ต้องเป็น data URI ไม่ใช่ path หรือ URL ภายนอก

สองเหตุผล: ไฟล์ HTML ไฟล์เดียวต้องเป็นเด็คทั้งใบเหมือนที่ `.pptx` เป็น (ส่งต่อได้ ย้ายเครื่องได้) และ Canva เขียนไว้ตรง ๆ ว่ารูปกับฟอนต์ที่โฮสต์ข้างนอก "อาจไม่ตามมา" ตอนอิมพอร์ต HTML

ตัวลดทอนไป `.pptx` ต้องถอด data URI กลับเป็นไบต์ ซึ่ง `skill.loadPicture` วันนี้รับแต่ path ต้องเพิ่มทางนั้นตอนทำข้อ 2

## ที่ทางในหน้าจอ

**ห้องสไลด์เป็นแท็บ singleton** เหมือนไฟล์กับเครื่องมือ (`kind: 'decks'`, `DeckRoom.svelte`) ไม่ใช่แท็บต่อเด็ค เพราะคำถามที่มันตอบคือ "งานนำเสนอที่ทำไว้มีอะไรบ้าง" ซึ่งถามตอนยังไม่รู้ว่าจะเปิดไฟล์ไหน แพเนลไฟล์จึงตอบแทนไม่ได้

ห้องไม่มีตัวอ่านของตัวเอง มันยืม `SlidesPane` มาทั้งตัว ทั้งการเดินสไลด์ การนำเสนอ และแถบส่งออก ถ้าห้องมีตัวอ่านของตัวเองก็จะมีสองที่ที่ตอบคำถามเดียวกันว่าเด็คหน้าตายังไง

**รายการผูกกับโปรเจกต์ที่เปิดอยู่** ไม่ใช่ทุกรากที่แกลเลอรีกวาด และนั่นเป็นข้อจำกัดของไฟล์โฮสต์ ไม่ใช่การตัดสินใจเชิงผลิตภัณฑ์ — `filehost.go` รีโซลฟ์เทียบ `SandboxRoot` เด็คจากโปรเจกต์อื่นจึงเรนเดอร์ที่นี่ไม่ได้ และแถวที่เปิดแล้วว่างเปล่าแย่กว่าแถวที่ไม่มี

## สิ่งที่สัญญานี้ยังไม่ตอบ

- **PNG/JPG ต่อแล้ว แต่พิงข้อสันนิษฐานที่ยังไม่มีเอกสารรับรอง** หน้าต่างส่งออกจอดนอกจอแบบ `WS_VISIBLE` ไม่ใช่ `SW_HIDE` ซึ่งเป็นคนละสถานะกับที่ issue #1077/#2983 พูดถึง วินโดวส์ควร compose ให้เหมือนมีคนดูอยู่ ถ้าข้อสันนิษฐานนี้ผิดบนเครื่องไหน `notBlank` จะจับภาพสีเดียวล้วนแล้วขึ้น error แทนที่จะเขียนโฟลเดอร์ของสี่เหลี่ยมเปล่า
- **PDF ต่อแล้วแต่ยังไม่ได้ลองบนเครื่องจริง** แพตช์ที่สี่ผูก `CallDevToolsProtocolMethod` แล้วเรียก `Page.printToPDF` ผ่าน CDP แทนที่จะผูก `ICoreWebView2_7` กับอีกสามอินเทอร์เฟซ ไมโครซอฟท์ไม่ได้เขียนเอกสารว่าเมธอดนี้ทำงานบน CDP ของ WebView2 หรือไม่ ถ้าเครื่องปฏิเสธ ทางถอยคือ `_16::PrintToPdfStream` ได้ผลเท่ากัน
- **`slides_write` ยังอยู่** ห้องกับตัวส่งออกไม่ได้แตะมัน การลบทิ้งแล้วแทนด้วย `export` คือข้อ 2 ของลำดับ และเป็นจุดที่บล็อกเครื่องมือได้โทเคนคืน
- **ตัวเขียนยังไม่รู้เรื่องสัญญานี้** `AGENT.md` ของเด็คยังสอนวินัยแบบ `slides_write` และ STARTERS ยังสัญญา `.pptx` ไว้ ๕ จุด × ๒ ภาษา จนกว่าจะแก้ตรงนั้น เอเจนต์จะยังไม่เขียน HTML ออกมาเอง
