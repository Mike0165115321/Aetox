# What should we automate?

- A workflow that does the repetitive part for me | I want this job to run itself. Ask me first what triggers it, how often it happens, where the data comes from and goes to, and how much damage one wrong run would do. That last one matters most, because it decides whether this should run unattended or wait for someone to confirm. Read the skill for whichever tool we are using before you build — do not guess the shape of a node. Lay the steps out for me once before building anything. When it is built, run it against real data once. Do not tell me it is done because it saved: saving and running are different things. | gitBranch
- Where the workflow I already have will break first | Look at the existing workflow and tell me where it breaks first. Read every step before concluding anything. Look for four things: steps calling something external with no handling for it being slow or down, steps that produce a duplicate effect if re-run such as sending an email twice or creating a record twice, steps reading a value from an earlier step without checking it exists, and things that expire such as tokens or permissions nobody is watching. For each, say which step, what the user would see when it breaks, and how to fix it. Order by how often it breaks times how much it costs, not by position in the flow. | alertTriangle
- Why this run failed | This workflow failed — find out why. Open the actual run history first rather than reading the diagram and guessing. Find which step failed and what the data going into it looked like at that moment, because most of the time the problem is data in a shape the step did not expect, not the step itself. Establish whether it fails every time or only sometimes — those are traced differently. If it is intermittent, compare the data on a run that passed against one that failed. Close with the cause you are most confident in and the evidence for it, and only then propose a fix. Do not fix before you know what broke. | bandage
- A workflow tested properly before it goes live | Test this workflow before I turn it on. Do not only run it with the cleanest possible data. Try four cases: normal data, data with a required field empty, data in an unexpected format, and the same data twice to see whether it duplicates its effect. Report each case and what happened, and which ones produced something other than what should happen. If testing would create or send something real, tell me first and wait for me to approve rather than running it. Close with a single verdict: is this safe to turn on, or does something have to change first? | check
- The same workflow, moved to the other tool | Move this workflow to the other tool. Read the original until you understand what it is for, not merely what steps it contains, because the two tools do not have the same nodes. Read the destination tool's skill first so you know what a step looks like there. Give me a mapping table before you build: which steps port directly, which have to be rewritten, and which the destination cannot do at all. That last group has to be named before you start, not discovered halfway through. Do not delete or disable the original until the new one has actually run successfully. | package
- Which of my repetitive jobs to automate first | I have several jobs I repeat — work out which to automate first. Ask me what they are, how often each happens, how long one round takes, whether the steps are fixed or need judgement, and how quickly I would notice a mistake. Leave anything that needs judgement every time alone no matter how often it happens, or we build a system that needs babysitting. Rank by time saved per month divided by difficulty to build, and say plainly which ones should not be automated at all and why. Close with the single one to start with, and the reason. | brain
- A workflow that tells me when it fails | Make this workflow tell me when it fails. The problem now is that it is silent: it fails and nobody knows until somebody stumbles on it later. First check what currently happens when a step fails — does it stop, or carry on with incomplete data? The second is more dangerous because it looks like success. Make every failure send me a message carrying three things: which step failed, what data caused it, and whether the run stopped or continued. Do not just send the word "error". Where a failure is transient and a retry would clear it, retry first and only tell me if it still fails, so I am not flooded. | shield
- I have never connected an automation tool — where do I start? | I have never used an automation tool. Where do I start? Explain first how this room works: Aetox is not the clock — it connects to an automation tool you already run, such as n8n or Windmill, and acts as its hands. Say how those two differ and who each suits, from the facts, without pushing either. Then walk me through what to fill in on the connections page, in short steps. Close with a good first job for a beginner: one where a mistake costs nothing and the result is visible immediately. Do not propose something touching money or reaching customers as a first job. | plug
