# What should we look at on GitHub?

- Whether this PR should be merged | Review this pull request. Read the pr-workflow skill first. Read the whole diff, every file, before you comment on anything — do not review from the title or the description, which only tell you what the author intended. Check three layers: does the code do what it says it does, is there a case where it breaks, and is there anything in here that does not belong in the same PR. Give file and line for each point, and mark each one as blocking or as an observation — do not blend the two. Close with a single verdict: merge it, fix first, or split it. If you find nothing wrong, say so. | gitBranch
- Why CI is actually red | CI is red — find out why. Read the ci-triage skill first. Read the failing job's log down to the line that actually broke, not the summary line at the end, which usually says what failed and not why. Separate three things: a real failure caused by the change, a test that was already flaky, and an environment problem such as network, cache, or quota — each is fixed a different way. If you are going to call it flaky, show evidence from earlier runs rather than guessing. Close with the next steps, ordered by which one proves or disproves the theory fastest. | alertTriangle
- Which of the open issues to do first | Go through the open issues and order them. Read the issue-hygiene skill first. Read all of them before ranking anything, rather than judging one at a time — several will turn out to be the same thing reported by different people. Pair the duplicates but do not close anything yourself. Rank on two axes together: how many people it affects, and whether fixing it unblocks other work — not by which is oldest. Put the ones with too little information to start into their own pile with a note on what is missing. Close with the five to do first, one line of reasoning each, and say which ones should be closed as no longer relevant. | layoutList
- What this repo still needs before others can use it | Check whether this repository is ready for other people to use or contribute to. Read the repo-standards skill first, then look at what is actually in the repo — do not infer from the project name. Check whether there is a README that says what this is and how to start, a licence, instructions to run it locally, instructions to run the tests, and a stated way to report a problem or send work in. For each, say whether it is there, there but insufficient, or missing. Order the work by what a newcomer hits in the first minute, not by the order in the skill, and do not propose things a project this size does not need yet. | shield
- Release notes, from what actually merged | Write the release notes. Work from what actually merged in the given window, not from what was planned. If I have not given you a window or a tag, ask. Group by what a user can feel — new, fixed, and changed in a way that requires them to adapt — not by module. Roll internal work nobody notices into a single line. Write each entry from the user's side: what they can do now that they could not before. Do not paste commit subjects. Anything that breaks existing usage goes at the top, with what to do about it. | package
- A PR description a reviewer can actually follow | Write the description for this pull request. Read the diff yourself first rather than writing from what I told you — what the code does and what I believe it does may differ. Cover four things: what the problem was, how it is solved, why this way rather than the more obvious way, and where the reviewer should look hardest. The last one matters most — do not write "review everything"; name real files. Say how it was tested and how you know it works, and if it was not tested, say that plainly rather than writing around it. If this diff is too large to review as one PR, say how it should be split. | pencil
- How this code came to look like this | Trace how this piece of code ended up this way. Read the current file first so you understand what it does now, then work backwards through who changed what and what problem they were solving at the time. Care about why more than when. A line that looks strange and invites deletion is usually guarding a case that broke once — find that case before concluding it can go, and if you cannot find a reason, say you could not. Close with a short summary of what this section is for, what assumptions are buried in it, and where anyone changing it should tread carefully. | search
- An issue somebody else can pick up | Write this issue up. Read the issue-hygiene skill first. Ask me until you have all of it: what the symptom is, what was done to hit it, what was expected versus what happened, whether it happens every time or sometimes, and on what machine and version. If it is a feature request, ask what I am doing instead today, because that says how urgent it is. Write a title that tells a reader what this is about without opening it — not "there is a problem". Before filing, search for an existing issue, and if one exists, tell me instead of opening a duplicate. | messageSquare
