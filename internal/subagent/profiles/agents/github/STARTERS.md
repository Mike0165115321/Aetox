# จะให้ดูอะไรใน GitHub ดี?

- รู้ว่า PR ใบนี้ควร merge ไหม | ช่วยรีวิว PR ใบนี้ให้หน่อย เปิดสกิลเรื่องการรีวิว PR อ่านก่อน อ่าน diff ให้ครบทุกไฟล์ก่อนจะเริ่มคอมเมนต์ อย่ารีวิวจากชื่อ PR หรือคำอธิบาย เพราะทั้งสองอย่างนั้นบอกได้แค่ว่าคนเขียนตั้งใจอะไร ดูสามชั้น ชั้นแรกโค้ดนี้ทำสิ่งที่บอกว่าจะทำจริงไหม ชั้นที่สองมีเคสไหนที่โค้ดนี้จะพัง ชั้นที่สามมีอะไรในนี้ที่ไม่ควรอยู่ใน PR ใบเดียวกัน แต่ละข้อบอกไฟล์และบรรทัด และบอกว่าเป็นข้อที่ต้องแก้ก่อน merge หรือแค่ข้อสังเกต อย่าปนกัน ปิดท้ายด้วยคำตอบเดียวว่า merge ได้ ต้องแก้ก่อน หรือควรแยกเป็นหลายใบ ถ้ารีวิวแล้วไม่เจอปัญหาให้บอกว่าไม่เจอ | gitBranch
- รู้ว่า CI แดงเพราะอะไรจริง ๆ | CI แดงอยู่ ช่วยไล่หาสาเหตุให้หน่อย เปิดสกิลเรื่องการไล่ CI อ่านก่อน อ่าน log ของ job ที่ล้มให้ถึงบรรทัดที่พังจริง อย่าหยุดที่บรรทัดสรุปท้าย เพราะบรรทัดนั้นมักบอกแค่ว่าอะไรล้ม ไม่ได้บอกว่าเพราะอะไร แยกให้ชัดว่านี่คือของพังจริงจากโค้ดที่เพิ่งเปลี่ยน หรือเป็นเทสต์ที่ล้มไม่แน่นอนอยู่แล้ว หรือเป็นปัญหาสภาพแวดล้อมอย่างเน็ตหรือแคชหรือโควตา สามอย่างนี้แก้คนละทาง ถ้าจะบอกว่าเป็นเทสต์ที่ล้มไม่แน่นอน ต้องมีหลักฐานจากรันก่อนหน้ามาแสดง อย่าเดา ปิดท้ายด้วยขั้นตอนที่ต้องทำต่อ เรียงจากอันที่พิสูจน์สมมติฐานได้เร็วที่สุด | alertTriangle
- รู้ว่า issue ที่ค้างอยู่ควรทำอะไรก่อน | ช่วยดู issue ที่ค้างอยู่แล้วจัดลำดับให้หน่อย เปิดสกิลเรื่องการดูแล issue อ่านก่อน อ่านทุกใบก่อนจะเริ่มจัดอันดับ ไม่ใช่ไล่ตัดสินไปทีละใบ เพราะหลายใบเป็นเรื่องเดียวกันที่คนละคนแจ้ง ใบที่ซ้ำกันให้จับคู่ไว้ อย่าปิดเอง จัดลำดับจากสองแกนคู่กัน คือกระทบคนกี่คน กับแก้แล้วปลดล็อกงานอื่นได้ไหม ไม่ใช่จากว่าใบไหนเก่าสุด ใบที่ข้อมูลไม่พอจะเริ่มทำ ให้แยกไว้กองหนึ่งพร้อมบอกว่าขาดอะไร ปิดท้ายด้วยรายชื่อห้าใบที่ควรทำก่อนพร้อมเหตุผลใบละหนึ่งบรรทัด และบอกว่ามีใบไหนที่ควรปิดเพราะหมดอายุไปแล้ว | layoutList
- รู้ว่ารีโปนี้ยังขาดอะไรถึงให้คนอื่นใช้ได้ | ช่วยดูว่ารีโปนี้พร้อมให้คนอื่นเข้ามาใช้หรือมาช่วยพัฒนาหรือยัง เปิดสกิลเรื่องมาตรฐานรีโปอ่านก่อน แล้วไล่ดูของจริงในรีโป อย่าเดาจากชื่อโปรเจกต์ ดูว่ามี README ที่บอกได้ไหมว่านี่คืออะไรและเริ่มยังไง มีสัญญาอนุญาต มีวิธีรันในเครื่อง มีวิธีรันเทสต์ และมีทางบอกว่าจะรายงานปัญหาหรือส่งงานเข้ามายังไง แต่ละข้อบอกว่ามีอยู่แล้ว มีแต่ไม่พอ หรือไม่มีเลย เรียงตามลำดับที่ควรทำก่อนหลัง โดยเอาข้อที่คนใหม่จะติดตั้งแต่นาทีแรกขึ้นก่อน อย่าเรียงตามลำดับในสกิล และอย่าเสนอของที่โปรเจกต์ขนาดนี้ยังไม่จำเป็นต้องมี | shield
- ได้ release note จากสิ่งที่ merge ไปแล้วจริง | ช่วยเขียน release note ให้หน่อย อ่านจากสิ่งที่ merge เข้าไปจริงในช่วงที่กำหนด ไม่ใช่จากแผนที่ตั้งใจจะทำ ถ้าไม่ได้บอกช่วงเวลาหรือแท็ก ให้ถามก่อน จัดกลุ่มตามสิ่งที่ผู้ใช้รู้สึกได้ ของใหม่ ของที่แก้แล้ว และของที่เปลี่ยนจนต้องปรับตัว ไม่ใช่จัดกลุ่มตามโมดูลในโค้ด งานภายในที่ผู้ใช้ไม่รู้สึกอะไรเลยให้รวบเป็นบรรทัดเดียว เขียนแต่ละข้อในมุมของคนใช้ว่าตอนนี้ทำอะไรได้ที่เมื่อก่อนทำไม่ได้ ห้ามลอกหัวข้อคอมมิตมาวาง ของที่เปลี่ยนจนของเดิมพัง ต้องขึ้นบนสุดพร้อมบอกว่าต้องทำอะไรถึงจะข้ามมาได้ | package
- ได้คำอธิบาย PR ที่คนรีวิวอ่านแล้วเข้าใจ | ช่วยเขียนคำอธิบาย PR ใบนี้ให้หน่อย อ่าน diff เองก่อน อย่าเขียนจากที่ฉันเล่า เพราะสิ่งที่โค้ดทำกับสิ่งที่ฉันคิดว่าโค้ดทำอาจไม่ตรงกัน เขียนสี่ส่วน ปัญหาคืออะไร แก้ด้วยวิธีไหน ทำไมเลือกวิธีนี้แทนวิธีที่ชัดกว่า และคนรีวิวควรดูตรงไหนเป็นพิเศษ ส่วนสุดท้ายสำคัญที่สุด อย่าเขียนว่าดูทั้งหมด ให้ชี้ไฟล์จริง บอกด้วยว่าทดสอบยังไงถึงรู้ว่ามันใช้ได้ ถ้าไม่ได้ทดสอบให้บอกว่าไม่ได้ทดสอบ อย่าเขียนคลุมเครือ ถ้า diff นี้ใหญ่เกินกว่าจะรีวิวได้ในใบเดียว ให้บอกว่าควรแยกยังไง | pencil
- รู้ว่าโค้ดส่วนนี้ใครแตะล่าสุดและเปลี่ยนอะไร | ช่วยไล่ให้หน่อยว่าโค้ดส่วนนี้กลายมาเป็นแบบนี้ได้ยังไง อ่านไฟล์ปัจจุบันก่อนให้เข้าใจว่ามันทำอะไรอยู่ แล้วค่อยไล่ย้อนว่าใครเปลี่ยนอะไรและตอนนั้นเขาแก้ปัญหาอะไรอยู่ สนใจว่าทำไมมากกว่าว่าเมื่อไหร่ บรรทัดที่ดูแปลกและอยากลบทิ้ง มักเป็นบรรทัดที่ใส่ไว้กันเคสที่เคยพังมาแล้ว ให้ตามหาเคสนั้นให้เจอก่อนสรุปว่าลบได้ ถ้าตามแล้วไม่เจอเหตุผลก็ให้บอกว่าไม่เจอ ปิดท้ายด้วยสรุปสั้นว่าส่วนนี้ตั้งใจทำอะไร มีข้อสมมติอะไรซ่อนอยู่ และมีตรงไหนที่ถ้าจะแก้ต้องระวังเป็นพิเศษ | search
- เขียน issue ที่คนอื่นหยิบไปทำต่อได้ | ช่วยเขียน issue ใบนี้ให้หน่อย เปิดสกิลเรื่องการดูแล issue อ่านก่อน ถามฉันจนได้ครบว่าเจออาการอะไร ทำอะไรถึงเจอ คาดว่าจะเกิดอะไรแต่จริง ๆ เกิดอะไร เกิดทุกครั้งหรือบางครั้ง และบนเครื่องแบบไหนเวอร์ชันไหน ถ้าเป็นข้อเสนอฟีเจอร์ให้ถามว่าตอนนี้เลี่ยงด้วยวิธีอะไรอยู่ เพราะนั่นบอกว่าเรื่องนี้เร่งแค่ไหน เขียนชื่อเรื่องให้คนอ่านแล้วรู้เลยว่าเรื่องอะไรโดยไม่ต้องกดเข้าไป อย่าเขียนว่ามีปัญหา ก่อนส่งให้ค้นก่อนว่ามีใบเดิมอยู่แล้วไหม ถ้ามีให้บอกฉันแทนที่จะเปิดใบใหม่ซ้ำ | messageSquare
