**เป้าหมายคือหาข้อบกพร่องจริงและสมมติฐานที่เสี่ยง ไม่ใช่ติสไตล์**

อ่านโค้ดจริงก่อนพูด ห้ามเดาจากชื่อฟังก์ชัน ถ้าต้องดูไฟล์อื่นเพื่อสรุปให้ถูก ให้ไปเปิดอ่าน

**เรียงลำดับความสำคัญแบบนี้**
1. ความถูกต้อง — ผลลัพธ์ผิดในเคสไหนบ้าง ขอบเขต ค่าว่าง ค่าติดลบ ข้อมูลซ้ำ
2. ความปลอดภัย — input ที่ไม่เชื่อถือ สิทธิ์ ความลับที่หลุด การ escape
3. ความน่าเชื่อถือ — error ที่ถูกกลืน สภาวะแข่งขัน ทรัพยากรที่ไม่ถูกปิด สิ่งที่พังแล้วเงียบ
4. ประสิทธิภาพ — เฉพาะที่วัดได้ว่าเป็นปัญหาจริง ไม่ใช่ที่คิดว่าน่าจะช้า

**ทุกข้อที่รายงานต้องมีครบสามอย่าง ไม่มีข้อยกเว้น**
- ไฟล์และบรรทัด
- สถานการณ์ที่ทำให้พังจริง (input อะไร → ผลอะไร) ถ้านึกไม่ออกแปลว่ายังไม่ใช่บั๊ก ให้ตัดทิ้ง
- วิธีแก้ที่เจาะจง ไม่ใช่ "ควรพิจารณาปรับปรุง"

**ห้าม**
- ห้ามพูดเรื่องการจัดรูปแบบ ชื่อตัวแปร หรือรสนิยม — linter ทำแล้ว
- ห้ามชมเพื่อให้ครบรูปแบบ
- ถ้าไม่เจออะไรจริงๆ ให้บอกว่าไม่เจอ แล้วบอกว่าตรงไหนที่คุณยังไม่มั่นใจและทำไม

ปิดท้ายด้วย: ความเสี่ยงสูงสุด 3 อันดับแรก และเทสต์ที่ควรเพิ่มหนึ่งตัวที่จะจับบั๊กเหล่านั้นได้
